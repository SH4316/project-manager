## 1. 가장 큰 결정: 배제 근거가 사라졌다

GUIDE-00과 PLAN.md는 슬래시 명령을 **명시적으로 제외**했다. 근거는 이랬다.

> core는 서명 검증(pynacl/cryptography)도, 새 공개 엔드포인트도 갖지 않았다 — HTTP 인터랙션 대신
> 게이트웨이 DM을 쓰기 때문이고, 이것이 이 설계의 가장 큰 이득이다.

그 근거는 **HTTP 인터랙션 엔드포인트**를 전제한다. 그런데 `discord.py`는 인터랙션을 **게이트웨이(WebSocket)로**
받는다. 공개 엔드포인트도, Ed25519 서명 검증도, 새 의존성도 필요 없다. `discord.py`는 이미 2.7.1로 묶여 있고
`app_commands`를 완전히 지원한다.

**그래서 슬래시 명령은 이 설계의 이득을 깨지 않고 들어온다.** core는 여전히 Discord로 나가는 요청을 하지 않고,
새 공개 엔드포인트도 생기지 않는다(봇 전용 라우터에 경로만 늘어난다).

이 문서가 그 배제 결정을 뒤집는다. GUIDE-00 §3의 "버튼·슬래시 명령·인터랙션 엔드포인트는 제외" 문장은
**"HTTP 인터랙션 엔드포인트는 여전히 제외. 슬래시 명령은 게이트웨이로 받는다"**로 고친다. 버튼·셀렉트 등
컴포넌트 인터랙션은 계속 제외다(상태 보관이 필요해 값어치보다 비싸다).

## 2. 실제 비용: 봇이 길드에 들어간다

지금 봇은 길드에 아예 없다. `listener.py`는 `Intents.none()` + `dm_messages` 하나이고,
`message.guild is not None`이면 즉시 버린다. 이것이 바뀐다.

| 항목 | 지금 | 바뀐 뒤 | 왜 |
|---|---|---|---|
| 인텐트 | `dm_messages` | `dm_messages` + `guilds` | 길드 캐시가 있어야 채널을 만든다. 둘 다 **비특권**이다 |
| OAuth 범위 | `bot` | `bot` + `applications.commands` | 슬래시 명령 등록 |
| 봇 권한 | (없음) | **Manage Channels** | 채널 생성. 이것만 준다 |
| 특권 인텐트 | 없음 | **없음** | `MESSAGE_CONTENT`·`GUILD_MEMBERS`·`PRESENCE`는 계속 켜지 않는다 |

**Manage Channels 외의 권한은 주지 않는다.** 특히 Manage Roles·Manage Server·Administrator는 받지 않는다 —
채널 생성에 필요하지 않고, 받으면 봇 토큰 유출 시 피해 범위가 서버 전체가 된다.

새 환경 변수는 하나다. `.env.discord`에 둔다.

```
DISCORD_GUILD_ID=   # 슬래시 명령을 등록하고 채널을 만들 길드
```

길드를 조직 모델에 넣지 않는 이유: v1은 조직 하나·길드 하나다. 여러 길드를 쓰게 되면 그때
`Organization.discord_guild_id`로 옮긴다. `# ponytail: 길드 1개 가정, 다중 길드가 필요하면 조직 필드로.`

## 3. 행위자와 인가 — 기존 계약을 그대로 쓴다

`core/api/routers/discord.py`의 계약이 이미 정답이다. 봇은 자기 이름으로 일하지 않는다.

```
interaction.user.id  →  core가 discord_user_id로 PM 사용자를 찾는다
                     →  없으면 "연결되지 않은 Discord 계정입니다"
                     →  있으면 그 사람의 권한 안에서만 움직인다
이력: actor=그 사람, source="dc", token=봇 토큰
```

슬래시 명령도 **똑같이** 한다. 새 인가 방식을 만들지 않는다.

**길드에서 특히 중요한 점:** DM은 상대가 곧 행위자지만, 길드 채널에서는 누구나 명령을 부를 수 있다.
연결되지 않은 사람, 조직 멤버가 아닌 사람이 부르는 것이 정상 상황이다. 거절이 **조용해야** 한다(§8).

채널 생성은 여기에 둘을 더 요구한다.

1. **PM 조직 관리자여야 한다**(`require_admin`). 채널을 만드는 것은 조직 구조를 바꾸는 일이고, 팀 만들기와
   같은 등급이다.
2. **그 사람이 Discord 길드에서 직접 Manage Channels 권한을 갖고 있어야 한다**
   (`interaction.user.guild_permissions.manage_channels`). 이것이 없으면 봇이 권한을 올려 주는 통로가 된다 —
   Discord 서버 관리자가 아닌 PM 관리자가 봇의 권한을 빌려 손으로는 못 만드는 채널을 만들게 된다. 봇은
   그 사람이 이미 가진 것보다 큰 Discord 권한을 주지 않는다. 이 검사는 core를 부르기 전에, 가장 먼저 한다.
   길드 인터랙션의 payload에 멤버·역할이 실려 오므로 `guilds` 인텐트만으로 풀린다(특권 인텐트 불필요).
   풀리지 않으면 거절한다(fail closed). 채널 명령은 길드 전용으로 등록해 DM에서는 아예 부를 수 없게 한다.

거절 문구는 둘을 구분한다. 사람에게 권한이 없으면 "Discord 서버에서 채널 관리 권한이 있어야 합니다.",
봇에게 없으면 "봇에게 채널 관리 권한이 없습니다…" — 고치는 사람이 다르다.

## 4. 새 모델 필드

새 앱도, 새 모델도 만들지 않는다. 두 필드만 늘린다.

```python
# orgs.Team
discord_channel_id = models.CharField("Discord 채널", max_length=32, blank=True)

# projects.Project
discord_channel_id = models.CharField("Discord 채널", max_length=32, blank=True)
```

삭제된 `teams.DiscordWebhook`을 되살리는 것이 아니다. 그것은 **비밀값(웹훅 URL)** 저장이라 지웠다.
채널 id는 비밀이 아니고, 보내는 주체는 계속 봇이다. core는 이 값을 **저장하고 보여줄 뿐** Discord로
나가지 않는다.

관리 화면은 만들지 않는다. 팀·프로젝트 화면에 연결된 채널을 **읽기 전용 한 줄**로 보이면 충분하다.

## 5. core 새 엔드포인트

전부 `core/api/routers/discord.py`(봇 전용 `BotTokenAuth` 라우터)에 넣는다. 세션·읽기·쓰기 토큰은
구조적으로 이 경로에 들어오지 못한다.

모든 요청 본문은 기존 `DiscordActorIn`처럼 `discord_user_id`를 싣는다. 식별자를 쿼리 문자열에
싣지 않으려고 조회도 POST다(기존 `/today`와 같은 이유).

| 메서드·경로 | 하는 일 | 인가 |
|---|---|---|
| `POST /projects` | 그 사람이 볼 수 있는 프로젝트 목록 (자동완성용, `{id, name, org_id}`) | 조직 멤버 |
| `POST /teams` | 그 사람이 볼 수 있는 팀 목록 | 조직 멤버 |
| `POST /tasks` | 태스크 생성 | 조직 멤버 |
| `POST /tasks/{id}/update` | 제목·중요도·기한·담당자·다음 행동 수정 | `get_visible_task` |
| `POST /tasks/{id}/note` | 진행 메모 덧붙이기 (`append_note`와 같은 의미) | `get_visible_task` |
| `POST /tasks/search` | 자동완성용 태스크 검색 (`{id, number, title}`) | 조직 멤버 |
| `POST /teams/{id}/channel` | 팀의 `discord_channel_id` 저장 | **조직 관리자** |
| `POST /projects/{id}/channel` | 프로젝트의 `discord_channel_id` 저장 | **조직 관리자** |

**채널 저장 엔드포인트는 채널을 만들지 않는다.** 봇이 만든 뒤 결과 id를 여기에 적는다. core가
Discord를 부르지 않는다는 규칙은 그대로다.

업무 규칙은 전부 `services.py`에 둔다. 라우터는 호출만 한다. 새 서비스 함수:

```python
# orgs/services.py
def set_team_channel(team, channel_id: str, actor) -> Team   # require_admin
# projects/services.py
def set_project_channel(project, channel_id: str, actor) -> Project   # require_admin
```

둘 다 빈 문자열을 받으면 연결을 끊는다(채널이 Discord에서 지워졌을 때).

## 6. 슬래시 명령

Discord 명령 이름은 소문자여야 하고 한글은 허용된다(`\p{L}`). 한글 이름을 쓴다.

### A단계 — 기존 DM 명령의 이식

| 명령 | 인자 | core 호출 |
|---|---|---|
| `/오늘` | — | 기존 `/today` |
| `/완료` | `번호` (태스크 자동완성) | 기존 `/tasks/{id}/done` |
| `/연장` | `번호`, `목표일`, `사유` | 기존 `/tasks/{id}/extend` |
| `/연결` | `코드` | 기존 `/link` |
| `/연결해제` | — | 기존 `/unlink` |
| `/도움` | — | 호출 없음 (문구만) |

**로직을 복제하지 않는다.** `commands.py`의 `_dispatch`가 이미 파싱·문구·오류 변환을 다 갖고 있다.
슬래시 핸들러는 같은 `CoreClient` 메서드와 같은 `messages.py` 문구를 쓴다. 파싱만 건너뛴다
(슬래시는 Discord가 인자를 나눠 준다).

### B단계 — 태스크 생성·편집

| 명령 | 인자 |
|---|---|
| `/태스크만들기` | `프로젝트`(자동완성, 필수), `제목`(필수), `기한`(선택), `기한미정사유`(선택), `중요도`(선택, 1~10), `담당자`(선택, 자동완성) |
| `/태스크수정` | `번호`(자동완성, 필수), `제목`·`기한`·`중요도`·`담당자`·`다음행동`(전부 선택) |
| `/메모` | `번호`(필수), `내용`(필수) |
| `/상태` | `번호`(필수), `상태`(Choice 7개), `사유`(선택) |

`기한`이 없으면 `기한미정사유`가 필요하다 — core가 그렇게 검증한다. 슬래시 쪽에서 미리 막지 않고
core의 오류 문구를 그대로 보여 준다(검증은 한 곳에만 둔다).

`상태`는 `app_commands.Choice`로 7개를 고정한다. 오타가 아예 불가능해진다.

### C단계 — 채널 생성

| 명령 | 인자 |
|---|---|
| `/팀채널` | `팀`(자동완성, 필수), `카테고리`(선택) |
| `/프로젝트채널` | `프로젝트`(자동완성, 필수), `카테고리`(선택) |

흐름 (§7).

## 7. 채널 생성 흐름

```
0. Discord 권한  interaction.user.guild_permissions.manage_channels 가 없으면 거절하고 끝. core를 부르지 않는다.
1. 인가      core에 물어 PM 사용자·조직 관리자 여부를 확인한다. 아니면 거절하고 끝.
2. 중복 확인  팀·프로젝트에 이미 discord_channel_id가 있으면
             그 채널이 길드에 실제로 있는지 본다.
               있다  → 만들지 않고 그 채널을 알려 준다.
               없다  → Discord에서 지워진 것이다. 계속 진행한다.
3. 생성      guild.create_text_channel(name, category=..., topic=...)
4. 되적기     core에 POST .../channel 로 채널 id를 저장한다.
5. 답장      만든 채널을 알려 준다(ephemeral).
```

**4번이 실패하면 3번을 되돌린다.** 채널만 생기고 연결이 없으면 다음 호출이 또 만들어 중복이 쌓인다.
되돌리기(채널 삭제)도 실패하면 그 사실을 답장에 적는다 — 조용히 삼키지 않는다.

채널 이름: 팀·프로젝트 이름을 그대로 쓴다. Discord는 채널 이름에 한글을 허용하고 공백을 하이픈으로
바꾼다. GitHub 팀 slug와 달리 깎이지 않는다.

`discord.Forbidden`은 **권한 안내로 번역한다**: "봇에게 채널 관리 권한이 없습니다. 서버 설정에서
Manage Channels를 주세요." 트레이스백을 사용자에게 보이지 않는다.

## 8. 답장은 전부 ephemeral

길드 채널은 공유 공간이다. `/오늘`의 결과는 그 사람의 업무 목록이고, 채널에 뿌리면 유출이다.
**모든 슬래시 응답은 `ephemeral=True`다.** 예외 없다 — 채널 생성 결과도 마찬가지고, 만들어진 채널
자체가 남는 증거다.

거절도 ephemeral이다. 연결되지 않은 사람이 길드에서 명령을 불렀을 때, 그 사실이 채널에 남지 않는다.

## 9. 구현이 반드시 지켜야 하는 것 셋

`listener.py`의 기존 주석이 두 개를 이미 말한다. 세 번째는 새로 생긴다.

1. **`CoreClient`는 동기 httpx다.** 이벤트 루프에서 그대로 부르면 하트비트가 굶어 게이트웨이가 끊긴다.
   반드시 `await asyncio.to_thread(...)`로 감싼다.
2. **`import discord`는 절대 임포트다.** 같은 패키지의 `discord_service/discord.py`가 아니라
   site-packages를 가리킨다. 새 파일에서도 그 전제가 유지되어야 한다.
3. **인터랙션은 3초 안에 응답해야 한다.** core 호출은 그보다 오래 걸릴 수 있다. 모든 핸들러는
   먼저 `await interaction.response.defer(ephemeral=True)`를 하고, 끝나면 `interaction.followup.send(...)`
   로 답한다. 자동완성 콜백은 defer할 수 없으므로(3초 내 반환 필수) core 호출을 짧게 유지한다.

명령 동기화는 `setup_hook`에서 **길드 범위로** 한다(`tree.sync(guild=...)`). `on_ready`는 재접속 때마다
다시 불리므로 거기서 동기화하면 매번 API를 때린다. 길드 범위 동기화는 즉시 반영되고, 전역 동기화는
최대 1시간 걸린다.

발신자별 분당 한도(`too_fast`, RATE=20)를 슬래시에도 적용한다. core의 처리량 제한은 봇 계정 하나로
세므로 한 사람이 다 쓰면 다른 사람이 429를 받는다.

| 파일 | 하는 일 |

| `core/projects/migrations/0004_project_discord_channel.py` | 필드 추가 |

`listener.py`는 `CommandTree`를 붙이고 `slash.register(tree, cfg, core)`를 부르는 정도만 늘어난다.
DM 처리 경로는 건드리지 않는다.

## 11. 단계와 검증

각 단계 끝에서 `uv run pytest -q`와 `uv run ruff check .`가 통과해야 다음으로 간다(GUIDE-00 §1).

| 단계 | 내용 | 검증 |
|---|---|---|
| 0 | core 필드 2개 + 서비스 2개 + 엔드포인트 8개 | core 테스트. 관리자 아닌 사람의 채널 저장이 거부되는지 |
| A | `/오늘`·`/완료`·`/연장`·`/연결`·`/연결해제`·`/도움` | 가짜 인터랙션으로 핸들러 테스트. DM 명령이 여전히 동작하는지 |
| B | `/태스크만들기`·`/태스크수정`·`/메모`·`/상태` + 자동완성 | 기한 없이 만들면 core 문구가 그대로 나오는지 |

채우는 것은 코드로 할 수 없다. 그 전까지는 가짜 인터랙션 테스트로만 확인한다.

## 12. 자동완성 — 이 기능의 사용성은 전부 여기 달려 있다

사람이 `12` 같은 숫자나 `산돌이 API` 같은 이름을 **외워서 타자하게 만들면 안 된다.** id를 받는 모든
인자는 자동완성을 가진다. 이것이 "체계적"의 실질이다.

### 규칙 1 — id를 받는 인자에는 예외 없이 자동완성을 붙인다

| 인자 | 보여 주는 것(name) | 실제로 보내는 것(value) | 정렬 |
|---|---|---|---|
| `번호` | `TASK-12 웹훅 재시도 로직 개선` | `12` | 기한 가까운 순, 기한 없는 것은 뒤 |
| `프로젝트` | `산돌이 API` | 프로젝트 id | 이름순 |
| `팀` | `백엔드` | 팀 id | 이름순 |
| `담당자` | `홍석영` | 사용자 id | 이름순 |

Discord의 `Choice(name=..., value=...)`가 정확히 이 구분을 준다. 사람은 읽을 것을 보고, 봇은 id를 받는다.
**숫자를 외우게 하지 않는다.**

### 규칙 2 — 고정된 집합은 자동완성이 아니라 Choice다

`상태`(7개)는 `app_commands.Choice`로 못 박는다. 자동완성은 자유 입력을 허용하므로 오타가 가능하지만,
Choice는 Discord가 목록에서만 고르게 한다. **오타가 구조적으로 불가능해진다.** 중요도도 티어가 필요하면
Choice로 하고, 1~10 자유 입력이면 `min_value=1, max_value=10`을 걸어 Discord가 먼저 막게 한다.

### 규칙 3 — 자동완성도 인가를 통과한다. 실패하면 빈 목록이다

**여기가 조용한 유출 지점이다.** 자동완성 콜백은 명령 실행이 아니라서 인가를 건너뛰기 쉽다. 그러나
길드에서는 연결되지 않은 사람, 조직 멤버가 아닌 사람이 `/완료 ` 까지만 입력하는 일이 정상이고, 그때
목록에 남의 태스크 제목이 뜨면 그것으로 유출이 끝난다.

- 자동완성도 `interaction.user.id`로 core에 물어 행위자를 정한다. 명령 실행과 **같은 경로**를 쓴다.
- 미연결·비멤버·core 오류·시간 초과는 **전부 빈 목록**을 돌려준다. 오류 메시지를 자동완성에 넣지 않는다
  (자동완성은 오류를 보여줄 자리가 아니고, 문구가 내부 사정을 흘린다).
- 즉 **fail closed**다. 실패하면 아무것도 보여 주지 않는다.

### 규칙 4 — 매 타자마다 core를 부르지 않는다

자동완성은 키 입력마다 발동한다. 분당 한도가 20이면 타자 스무 번에 소진된다. 그리고 3초 안에
반환해야 하는데 defer가 불가능하다.

**봇 프로세스 안에 짧은 TTL 캐시를 둔다.**

```
키:    (discord_user_id, 종류)        종류 = projects | teams | members | mytasks
값:    목록 전체 (수십 건 규모)
TTL:   30초
필터:  사용자가 입력한 문자열로 로컬에서 걸러낸다 (core를 다시 부르지 않는다)
```

그래서 core 호출은 **30초에 한 번**이고 타자는 전부 메모리에서 처리된다. 캐시는 `Store`(SQLite)에
넣지 않는다 — 프로세스 메모리의 dict로 충분하고, 오래 살아야 할 값이 아니다.
`# ponytail: 프로세스 메모리 dict, 봇이 여러 대가 되면 각자 캐시를 갖는다(문제 없음).`

**자동완성은 명령 실행과 같은 한도를 쓰지 않는다.** 같은 한도를 공유하면 타자가 명령을 굶긴다.
자동완성은 캐시 적중률이 높으므로 별도의 느슨한 한도(또는 한도 없음)로 둔다.

### 규칙 5 — 태스크 자동완성은 "내 미완료 태스크"다

조직 전체 태스크를 자동완성에 올리면 25개 상한에 걸려 쓸모가 없고, 캐시도 못 한다.

`/완료`·`/연장`·`/메모`·`/상태`의 `번호` 자동완성은 **그 사람의 미완료 태스크**를 보여 준다. 이유가 둘이다.
사용성 — 그 사람이 지금 손댈 태스크가 거기 있다. 그리고 캐시 가능성 — 한 사람의 미완료는 수십 건이다.

남의 태스크를 건드려야 하면 숫자를 직접 타자할 수 있게 남겨 둔다(자동완성은 제안일 뿐 제약이 아니다).
권한은 그때도 core의 `get_visible_task`가 본다.

`POST /tasks/search` 대신 이미 필요한 `POST /today`와 같은 성질의 조회를 쓴다 — 그 사람의 미완료 목록
하나면 네 명령의 자동완성이 전부 채워진다. **엔드포인트를 늘리지 않는다.**

### 규칙 6 — 인자 이름을 명령마다 다르게 짓지 않는다

같은 것을 뜻하는 인자는 같은 이름을 쓴다. 사람이 한 번 익히면 전부에 통한다.

```
번호 · 프로젝트 · 팀 · 담당자 · 기한 · 기한미정사유 · 중요도 · 상태 · 사유 · 내용 · 제목 · 다음행동 · 카테고리
```

`기한`은 어디서나 `YYYY-MM-DD`다. `사유`는 상태 변경·연장에서 같은 뜻이다. 새 이름을 만들기 전에
이 목록에 이미 있는지 본다.

### 규칙 7 — 25개를 넘기면 잘라내되, 잘렸다고 알린다

Discord는 25개까지만 받는다. 넘치면 정렬 기준 상위 24개를 주고, 마지막 한 자리에
`… 더 있습니다. 이름을 더 입력해 주세요`를 **선택 불가능한 안내로 넣지 않는다** — Choice는 전부 선택
가능해야 한다. 대신 상위 25개만 주고, 사용자가 더 입력하면 필터가 좁혀지게 둔다. 검색은 부분 일치로 한다.

## 13. 하지 않는 것

- **버튼·셀렉트 등 컴포넌트 인터랙션.** 상태 보관이 필요하고 값어치보다 비싸다.
- **HTTP 인터랙션 엔드포인트.** 게이트웨이로 받으므로 영원히 필요 없다.
- **채널 삭제·이름 변경 명령.** 만들기만 한다. 지우기는 사람이 Discord에서 한다(봇에게 삭제 권한을
  주지 않아도 되게 유지한다 — Manage Channels는 삭제도 포함하지만, 명령을 만들지 않으면 실수로 지울 일이 없다).
- **채널에 알림 라우팅.** 이 라운드는 채널을 **만들고 연결**만 한다. 마감 알림을 팀 채널로 보내는 것은
  후속이다(개인 DM이 기본이라는 결정은 유지).
- **여러 길드.** §2.
- **특권 인텐트.** 서버 멤버 목록·메시지 내용·프레즌스는 계속 받지 않는다.
