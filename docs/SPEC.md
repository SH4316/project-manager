# 산돌이 프로젝트 업무 관리 시스템 기능 명세서

버전: 0.1  
작성일: 2026-09-09  
범위: 최초 운영 버전(MVP)

## 1. 목적과 설계 원칙

프로젝트별 태스크, 담당자, 기한, 진행 상황을 명확하게 관리하고 AI Agent와 Discord에서 업무 정보를 쉽게 활용할 수 있는 팀 내부 웹 애플리케이션을 구축한다.

핵심 목표는 다음과 같다.

1. 팀원이 자신의 업무와 다음 행동을 빠르게 확인한다.
2. 담당자·프로젝트·기한 누락을 줄인다.
3. 웹과 AI에서 동일한 규칙으로 업무를 조회·수정한다.
4. 주간 업데이트와 마감 알림을 자동 제공한다.
5. 상시 운영자 없이 사용할 수 있도록 구성과 운영 부담을 최소화한다.

업무 데이터의 원본은 새 시스템으로 통일한다.

2026-09-11 변경: **"Notion을 회의록 저장소로 유지한다"는 결정을 폐기한다.** 회의록은 앱 안에서 관리하고(조직 단위, 마크다운 인라인 편집), Notion은 외부 공유용 링크로만 남긴다. 설계 문서·API 명세도 앱 안의 API 문서 화면과 참고 자료 링크로 옮겨 간다. 근거는 [IMPL-PLAN-2.md](IMPL-PLAN-2.md), 구현은 [GUIDE-V2-05](GUIDE-V2-05-notes.md)·[GUIDE-V2-06](GUIDE-V2-06-api-docs.md)에 있다.

## 2. 최초 버전의 범위

| 포함 | 제외 또는 후속 검토 |
|---|---|
| 팀원·프로젝트·태스크 관리 | 여러 조직에 제공하는 SaaS 기능 |
| 내 업무·프로젝트 현황·전체 현황판 | 사용자 정의 현황판 편집기 |
| 진행 메모·변경 이력·문서 링크·**회의록**(마크다운) | 파일 업로드·이미지 첨부·회의록 버전 이력 화면 |
| Discord 봇: 담당자 개인 DM 마감 알림 · 팀 채널 주간 보고 · DM 평문 명령(`오늘`·`완료`·`연장`·`연결`) | Discord 로그인(OAuth), 버튼·슬래시 명령, 자유 대화형 응답 |

| 고정된 업무 상태 | 사용자 정의 워크플로 |
| 단순 필터·정렬·검색 | 스프린트·스토리 포인트·간트 차트 |

2026-09-10 변경: '채널 알림'과 '태스크 수정 명령 제외'를 위와 같이 고쳤다. 알림은 채널이 아니라 **담당자 개인 DM**으로 가고(주간 보고만 채널), 봇에게 DM으로 보내는 평문 명령으로 태스크를 처리할 수 있다. Discord 로그인은 여전히 범위 밖이다 — 계정 연결은 웹에서 발급한 1회용 코드를 봇에게 DM으로 보내는 방식이고, 로그인 수단이 아니다.

2026-09-11 변경: 계층이 **조직 → 팀 → 멤버**로 바뀐다. 지금까지 "팀"이라 부르던 것이 **조직**이고, 조직 안에 분야별 **팀**(백엔드·프론트엔드 등)을 여럿 둔다. 한 사람은 여러 팀에 속할 수 있다. 팀은 가시성을 제한하지 않으며 GitHub 조직의 Team과 연결할 수 있다. 또한 GitHub 통합(저장소 연결·자동 상태 전환·조직과 팀 관리)이 범위에 들어온다. 자세한 것은 [IMPL-PLAN-2.md](IMPL-PLAN-2.md)에 있다.

최초 버전은 하나의 팀이 사용한다. 팀 내부 프로젝트와 업무는 모든 활성 팀원에게 공개한다. 비공개 프로젝트는 범위에 포함하지 않는다.

## 3. 사용자와 권한

### 3.1 로그인과 가입

- Discord 계정으로 로그인한다.
- 최초 로그인 사용자는 가입 대기 상태로 등록한다.
- 관리자가 승인한 사용자만 업무 데이터에 접근할 수 있다.
- 최초 관리자는 초기 설치 과정에서 지정한다.
- Discord 표시 이름이 바뀌어도 동일한 사용자로 식별한다.
- 탈퇴·비활성화된 사용자의 업무와 과거 이력은 보존한다.
- 비활성 사용자는 로그인과 API 접근을 할 수 없으며 신규 담당자로 지정할 수 없다.

Discord 로그인으로 얻는 사용자 식별자를 담당자 멘션에 사용한다.

### 3.2 권한 구분

| 기능 | 팀원 | 관리자 |
|---|---:|---:|
| 프로젝트·태스크 조회 | 가능 | 가능 |
| 프로젝트·태스크 생성 | 가능 | 가능 |
| 업무 내용·담당자·기한·상태 수정 | 가능 | 가능 |
| 댓글·문서 링크 추가 | 가능 | 가능 |
| 프로젝트 보관·복원 | 불가 | 가능 |
| 사용자 승인·역할 변경·비활성화 | 불가 | 가능 |
| Discord·AI·알림 설정 | 불가 | 가능 |
| 데이터 가져오기·내보내기 | 불가 | 가능 |

팀원은 공동 업무를 수정할 수 있다. 다른 사람의 업무를 수정한 경우에도 변경 전후 값과 수정자를 기록한다.

AI 연동 권한은 연결된 사용자 또는 전용 연동 계정의 권한을 넘을 수 없다.

## 4. 기본 데이터 구조

| 데이터 | 주요 항목 |
|---|---|
| 사용자 | ID, Discord 사용자 ID, 표시 이름, 역할, 활성 상태 |
| 프로젝트 | ID, 이름, 설명, 대표 담당자, 참여자, 상태, 목표일, 관련 링크 |
| 태스크 | ID, 제목, 설명, 대표 담당자, 대표 프로젝트, 관련 프로젝트, 상태, 중요도, 목표 기한 |
| 댓글 | 태스크, 작성자, 내용, 작성·수정 시각 |
| 문서 링크 | 연결 대상, 제목, URL, 종류 |
| 변경 이력 | 대상, 변경 항목, 이전 값, 이후 값, 행위자, 경로, 발생 시각 |
| 알림 기록 | 종류, 대상, 수신 채널, 기준 기한·기간, 발송 상태, 재시도 정보 |
| 주간 보고 | 보고 기간, 대상 프로젝트, 원본 집계, 요약문, 발송 결과 |
| 연동 자격 증명 | 소유자, 권한 범위, 만료 시각, 폐기 상태 |
| 이전 매핑 | 원본 Notion ID, 새 시스템 ID, 이전 결과 |

공통 규칙:

- 데이터는 표시 이름이 아닌 고유 ID로 연결한다.
- 태스크에 사람이 읽을 수 있는 고정 번호를 부여한다. 예: `TASK-123`.
- 시스템 발생 시각은 UTC로 저장한다.
- 날짜만 지정한 목표일은 시간으로 변환하지 않고 날짜로 보존한다.
- 기본 표시·알림 시간대는 `Asia/Seoul`로 한다.
- 변경 이력은 일반 사용자가 수정하거나 삭제할 수 없다.

## 5. 프로젝트 관리

### 5.1 프로젝트 정의

프로젝트는 서비스 또는 지속적으로 관리하는 업무 영역을 의미한다.

예: 학식 API, 카카오톡 챗봇, 서버 운영.

일회성 작업은 프로젝트가 아닌 태스크로 등록한다.

### 5.2 프로젝트 필드

| 필드 | 필수 | 설명 |
|---|---|---|
| 이름 | 필수 | 프로젝트를 식별하는 명칭 |
| 설명 | 선택 | 목적·범위에 대한 짧은 설명 |
| 대표 담당자 | 필수 | 프로젝트 진행을 책임지는 활성 팀원 |
| 참여자 | 선택 | 관련 팀원 목록 |
| 상태 | 필수 | 준비·진행·보류·종료 |
| 목표일 | 선택 | 프로젝트의 예정 목표일 |
| 저장소 링크 | 선택 | 관련 코드 저장소 |
| 문서 링크 | 선택 | Notion 문서 등 외부 자료 |
| 보관 여부 | 시스템 관리 | 기본 화면 노출 여부 |

프로젝트 상태와 태스크 완료율은 별개로 관리한다. 태스크가 모두 완료돼도 운영 중인 서비스의 프로젝트 상태를 자동으로 종료하지 않는다.

### 5.3 프로젝트 상세 화면

다음 정보를 표시한다.

- 프로젝트 이름·목적·대표 담당자·상태
- 미완료·기한 초과·검토 대기·막힌 업무 수
- 가장 가까운 목표 기한
- 프로젝트 태스크 목록
- 최근 변경 사항
- 저장소·문서 바로가기

프로젝트 화면에서 태스크를 만들면 해당 프로젝트가 대표 프로젝트로 자동 지정된다.

### 5.4 보관

- 종료된 프로젝트를 관리자가 보관할 수 있다.
- 미완료 태스크가 대표 소속으로 남아 있으면 보관을 막고 목록을 표시한다.
- 보관된 프로젝트는 기본 목록과 정기 알림에서 제외한다.
- 검색에서 ‘보관 포함’을 선택하면 조회할 수 있다.
- 보관은 데이터를 삭제하지 않으며 복원할 수 있다.

## 6. 태스크 관리

### 6.1 태스크 필드

| 필드 | 필수 | 설명 |
|---|---|---|
| 제목 | 필수 | 해야 할 일을 나타내는 명칭 |
| 설명 | 선택 | 작업 내용·완료 조건 |
| 대표 프로젝트 | 필수 | 태스크를 집계·관리하는 기본 프로젝트 |
| 관련 프로젝트 | 선택 | 함께 영향을 받는 추가 프로젝트 |
| 대표 담당자 | 필수 | 현재 작업 책임자 1명 |
| 중요도 | 필수 | 높음·중간·낮음, 기본값 중간 |
| 상태 | 필수 | 시작 전·진행 중·검토 대기·완료·취소 |
| 목표 기한 | 조건부 필수 | 미정이면 기한 미정 사유 입력 |
| 막힘 여부 | 선택 | 진행 불가 상태 표시 |
| 막힘 사유 | 조건부 필수 | 막힘 설정 시 필수 |
| 문서·PR 링크 | 선택 | 외부 자료와 결과물 |
| 생성·수정·완료 시각 | 자동 | 시스템이 기록 |

시작 전 태스크는 사유를 입력하면 기한을 미정으로 둘 수 있다. 진행 중으로 변경할 때는 목표 기한을 필수로 입력한다.

### 6.2 생성과 수정

- ‘내 업무’에서 생성하면 담당자를 본인으로 기본 지정한다.
- 프로젝트 화면에서 생성하면 대표 프로젝트를 자동 지정한다.
- 필수 항목 누락 시 저장하지 않고 해당 입력 항목에 오류를 표시한다.
- 과거 기한 입력은 허용하되 기한 초과임을 표시한다.
- 기한과 담당자를 변경하면 변경 이력을 기록한다.
- 사용자가 입력한 내용을 저장 실패 때문에 잃지 않도록 한다.
- 웹과 AI에서 동일한 검증 규칙을 적용한다.

### 6.3 상태와 완료 시각

일반적인 흐름은 다음과 같다.

`시작 전 → 진행 중 → 검토 대기 → 완료`

- 검토가 필요 없는 업무는 진행 중에서 바로 완료할 수 있다.
- 미완료 상태 사이의 이동을 허용한다.
- 미완료 태스크를 취소할 수 있다.
- 완료·취소 태스크는 사유를 입력하고 시작 전 또는 진행 중으로 재개할 수 있다.
- 완료 상태로 바뀌면 완료 시각을 자동 기록한다.
- 완료된 태스크에 같은 완료 요청이 반복돼도 완료 시각을 바꾸지 않는다.
- 재개하면 현재 완료 시각을 비우고, 이전 완료 사실은 이력에 남긴다.
- 재개 후 다시 완료하면 새로운 완료 시각을 기록한다.
- 취소는 완료 실적으로 집계하지 않는다.

완료 처리를 위해 별도 버튼 사용 규칙을 기억할 필요가 없어야 한다.

### 6.4 막힌 업무

막힘은 상태와 별도로 관리한다.

- 막힘을 설정할 때 사유를 입력한다.
- 막힌 시각을 자동 기록한다.
- 해제 시 해제 시각을 이력에 기록한다.
- 완료·취소 처리 시 현재 막힘 표시를 해제하고 이력은 보존한다.
- 현황판에서 막힘 기간과 사유를 확인할 수 있다.

### 6.5 여러 프로젝트에 걸친 업무

- 대표 프로젝트는 정확히 하나만 지정한다.
- 관련 프로젝트는 여러 개 지정할 수 있다.
- 관련 프로젝트 화면에도 동일한 태스크를 표시한다.
- 대표 프로젝트의 업무와 관련 업무를 구분해서 보여준다.
- 전체 현황판·주간 완료 건수는 태스크 ID를 기준으로 중복 제거한다.
- 주간 보고에서 태스크의 기본 분류는 대표 프로젝트를 사용한다.

### 6.6 댓글과 변경 이력

- 팀원은 태스크에 댓글 형태로 진행 메모를 작성할 수 있다.
- 댓글은 시간순으로 표시한다.
- 작성자는 자신의 댓글을 수정하거나 삭제할 수 있다.
- 댓글 수정·삭제 사실은 이력에 남긴다.
- 상태·담당자·기한·프로젝트·중요도 변경을 자동 기록한다.
- 웹 수정과 AI 수정을 구분해 표시한다.
- AI 수정은 연동 이름과 권한을 제공한 계정을 함께 기록한다.

최초 버전에서는 태스크 영구 삭제를 제공하지 않고 취소 상태로 처리한다.

## 7. 조회 화면과 현황판

### 7.1 내 업무

로그인 사용자의 업무를 다음 순서로 제공한다.

1. 기한 초과
2. 오늘 마감
3. 이번 주 마감
4. 그 이후 마감
5. 기한 미정

- 기본 목록에서 완료·취소는 제외한다.
- 프로젝트·상태·중요도·막힘으로 필터링할 수 있다.
- 목록에서 상태와 기한을 빠르게 수정할 수 있다.
- 각 항목에 제목·프로젝트·상태·기한·중요도를 표시한다.

### 7.2 프로젝트별 업무

- 목록 보기와 상태별 보드 보기를 제공한다.
- 대표 담당자·상태·기한·중요도로 필터링한다.
- 최초 버전은 상태 선택 메뉴로 이동을 지원한다. 드래그 이동은 필수 조건이 아니다.
- 완료·취소 업무는 선택해서 포함할 수 있다.

### 7.3 전체 현황판

| 지표 | 정의 |
|---|---|
| 미완료 | 시작 전·진행 중·검토 대기 태스크 |
| 기한 초과 | 미완료이며 목표 기한이 지난 태스크 |
| 이번 주 마감 | 이번 주 월요일부터 일요일까지 기한이 있는 미완료 태스크 |
| 검토 대기 | 현재 검토 대기 상태인 태스크 |
| 막힌 업무 | 미완료이며 막힘 표시가 있는 태스크 |
| 기한 미정 | 목표 기한이 없는 미완료 태스크 |
| 주간 완료 | 보고 기간 안에 완료 전환이 발생한 태스크, ID별 1건 |
| 재개 | 보고 기간 안에 완료·취소에서 미완료로 이동한 태스크 |

주간 완료 후 재개된 태스크는 재개 사실을 함께 표시한다.

현황판은 프로젝트별·담당자별 집계를 제공하고 숫자를 선택하면 해당 태스크 목록으로 이동한다.

### 7.4 검색

- 태스크 번호·제목, 프로젝트 이름으로 검색한다.
- 완료·취소·보관 데이터를 포함할지 선택한다.
- 검색 결과에 프로젝트·담당자·상태를 표시한다.
- 권한이 없는 사용자는 검색 API에서도 데이터를 조회할 수 없다.

## 8. Discord 알림

### 8.1 봇 설치와 계정 연결

- 운영자는 Discord 앱(봇)을 한 번 만들어 팀 서버에 설치한다. 봇 토큰은 서버 측 비밀 설정에만 둔다.
- 마감 알림은 담당자 **개인 DM**으로 보낸다. 팀 공통 채널 하나는 주간 보고와 운영 통보(DM을 보낼 수 없는 경우)에 쓴다.
- 프로젝트별 별도 채널은 만들지 않는다.
- 개인 DM을 받으려면 각자 자기 PM 계정과 자기 Discord 계정을 **연결**해야 한다. 연결은 웹에서 발급한 1회용 코드(10분)를 봇에게 DM으로 보내 이뤄진다.
- 사용자가 자기 Discord 사용자 ID를 직접 입력하는 경로는 두지 않는다. 한쪽만으로는 계정 소유가 증명되지 않는다.
- 연결을 끊으면 그 즉시 DM 알림이 멈춘다(수신 거부 수단을 겸한다).
- 확인 메시지는 발송 서비스의 명령으로 보낸다. 관리 화면은 두지 않는다.
- 봇 토큰과 연동 토큰은 일반 팀원이나 AI 조회 응답, 백업 내보내기에 노출하지 않는다.

### 8.2 마감 알림

기본 정책은 다음과 같다. 발송 시간은 서버 측 설정으로 바꾼다.

| 종류 | 기본 발송 기준 |
|---|---|
| D-3 | 목표일 3일 전 오전 9시 |
| D-1 | 목표일 1일 전 오전 9시 |
| 당일 | 목표일 오전 9시 |
| 기한 초과 | 매일 오전 9시 |

네 종류 모두 **담당자별로 묶어** 개인 DM 한 통으로 보낸다. 한 사람이 하루에 받는 알림은 종류당 1건, 최대 4건이다. 태스크마다 한 통씩 보내지 않는다.

- 날짜만 지정한 기한은 팀 시간대 기준 당일이 끝날 때까지 유효하다.
- 시각까지 지정한 기한은 해당 시각 이후 기한 초과로 판단한다.
- 발송 직전에 최신 상태·기한·담당자를 다시 확인한다.
- 완료·취소된 업무는 발송 대상에서 제외한다.
- 막힌 업무도 미완료이므로 알림에 포함한다.
- 기한이 바뀌면 이전 기한 기준의 미발송 알림을 무효화한다.
- 지나간 D-3·D-1 알림을 한꺼번에 소급 발송하지 않는다.
- 동일한 담당자·날짜·알림 단계 조합의 정상 발송은 반복하지 않는다.
- 담당자가 Discord를 연결하지 않았으면 그 사람 몫은 보내지 않고 **발송 기록도 남기지 않는다**(나중에 연결하면 다음 알림부터 정상으로 받는다). 미연결은 실패로 세지 않고, 주간 보고에 미연결자 명단 한 줄로 알린다.
- 그 사람이 DM을 막아 두어 Discord가 영구 거부를 답하면 재시도하지 않는다(실패로 기록한다). 대신 팀 공통 채널에 하루 한 번 DM 설정 안내를 올린다. 그 안내에는 태스크 제목·바로가기를 넣지 않는다.

개인 DM 메시지에는 태스크 번호·제목, 대표 프로젝트, 기한, 현재 상태, 바로가기, 그리고 답장으로 처리하는 방법 한 줄을 포함한다. 받는 사람 본인에게만 가므로 담당자 멘션은 넣지 않는다. 팀 채널 게시에는 담당자 멘션을 넣는다. 자동 `@everyone` 멘션은 사용하지 않는다.

### 8.2a DM 명령

담당자는 봇에게 보낸 개인 DM으로 자기 업무를 처리할 수 있다. 명령은 평문이며 다음 다섯 가지다.

| 명령 | 하는 일 |
|---|---|
| `오늘` | 오늘 화면과 같은 내용을 답장으로 받는다 |
| `완료 <번호>` | 그 태스크를 완료로 바꾼다 |
| `연장 <번호> <날짜> <사유>` | 목표일을 미루고 사유를 변경 이력에 남긴다 |
| `연결 <코드>` / `연결해제` | 계정 연결과 해제 |
| 그 밖의 텍스트 | 명령 목록을 답장한다 |

- 명령의 행위자는 **연결된 그 사람**이다. 변경 이력에는 그 사람과 변경 경로 `Discord`가 남는다. 볼 수 있는 범위도 그 사람의 팀으로 제한한다.
- 연결되지 않은 계정의 명령은 처리하지 않고 연결 방법을 답장한다.
- 웹에서 방금 바뀐 태스크에 대한 명령은 조용히 덮어쓰지 않고 다시 보내 달라고 답장한다.
- 명령 처리 실패는 한국어 한 줄로 답장한다. 같은 명령을 자동으로 재시도하지 않는다.

### 8.3 주간 업데이트

기본 발송 시점은 매주 월요일 오전 9시, 시간대는 `Asia/Seoul`이다.

보고 기간은 직전 월요일 00:00부터 이번 월요일 00:00 직전까지로 한다.

포함 내용:

- 지난주 완료한 태스크
- 지난주 재개한 태스크
- 주요 상태 변경과 진행 메모
- 이번 주 마감 예정
- 기한 초과와 막힌 업무
- 프로젝트별 짧은 요약
- 보고 기간과 원본 태스크 링크

특이 사항이 없으면 장문의 AI 요약 대신 간단한 상태 메시지를 보낸다.

### 8.4 실패 처리

- 일시적 실패와 요청 제한은 제한된 횟수 안에서 재시도한다.
- 발송 응답을 받지 못해 성공 여부가 불명확하면 해당 상태를 기록한다.
- 시스템이 알 수 있는 범위에서 중복을 방지하되 외부 전송의 절대적인 1회 발송은 보장하지 않는다.
- 장시간 중단 후 복구돼도 오래된 마감 알림을 대량 발송하지 않는다.
- 관리자는 최근 발송 성공·실패·미확정 기록을 조회할 수 있다.

## 9. AI Agent 연계

### 9.1 지원 기능

| 기능 | 동작 |
|---|---|
| 프로젝트 조회 | 프로젝트 정보·업무 현황·문서 링크 조회 |
| 태스크 검색 | 담당자·프로젝트·상태·기한 조건으로 조회 |
| 태스크 상세 | 설명·댓글·변경 이력 조회 |
| 태스크 생성 | 일반 생성 규칙에 따라 신규 업무 등록 |
| 태스크 수정 | 담당자·기한·중요도·내용 변경 |
| 상태 변경 | 완료·재개 등 공통 상태 규칙 적용 |
| 진행 메모 | 태스크에 댓글 추가 |
| 주간 요약 | 지정 기간의 집계와 변경 사항 설명 |

사용 예:

- “학식 API에서 이번 주 마감하는 업무 보여줘.”
- “TASK-123의 기한을 금요일로 변경해.”
- “내 진행 중 업무에 오늘 작업 내용을 남겨줘.”
- “지난주 프로젝트별 진행 상황을 요약해줘.”

사용자 계정 관리, 권한 변경, 연동 비밀값 조회, 영구 삭제는 AI 기능에서 제외한다.

### 9.2 API와 MCP

- 업무 규칙은 공통 서버 API 한 곳에서 처리한다.
- 웹 화면과 AI 연동은 같은 업무 API를 사용한다.
- MCP는 필요한 업무 API를 AI 도구로 제공하는 연결 계층으로 구현한다.
- AI가 DB에 직접 접근하거나 임의 SQL을 실행하지 않도록 한다.
- 목록 조회는 페이지 단위 조회와 결과 수 제한을 제공한다.
- 수정 요청에는 대상 ID와 수정할 항목을 명확하게 포함한다.
- 같은 요청의 재시도로 태스크·댓글이 중복 생성되지 않도록 요청 식별자를 지원한다.
- 조회 이후 다른 사용자가 변경했다면 충돌을 반환하고 최신 내용을 다시 확인하게 한다.

최초 버전의 MCP 도구 예:

`list_projects`, `get_project`, `list_tasks`, `get_task`, `create_task`, `update_task`, `transition_task`, `add_comment`, `get_weekly_report_data`

### 9.3 수정 권한과 모호한 요청

- 외부 AI 연결에는 범위가 제한된 연동 자격 증명을 사용한다.
- 자격 증명은 발급·만료·폐기할 수 있다.
- 예약 주간 요약 계정은 읽기 권한만 갖는다.
- 이름이 같은 사용자나 프로젝트가 여러 개면 AI가 임의 선택하지 않는다.
- 기한처럼 중요한 값이 모호하면 명확한 값으로 확인한 뒤 수정한다.
- 문서·댓글에 포함된 지시문이 권한이나 업무 규칙을 변경할 수 없도록 한다.

### 9.4 AI 요약의 정확성과 장애 대응

- 완료 건수·기한 초과·기간 계산은 서버에서 수행한다.
- AI는 제공받은 사실을 설명하는 역할을 맡는다.
- 모든 요약의 근거 태스크를 추적할 수 있어야 한다.
- 기록되지 않은 진척이나 완료를 추정해 단정하지 않는다.
- 외부 문서 링크의 본문 수집은 최초 버전에서 자동 수행하지 않는다.
- AI 실패 시 같은 집계 데이터를 사용한 고정 형식 보고서를 발송한다.
- AI 제공업체·모델·프롬프트는 업무 데이터 구조 변경 없이 교체할 수 있게 한다.
- 요청 시간·입력량·출력량·재시도에 상한을 둔다.

## 10. Notion 데이터 이전

### 10.1 이전 대상

- Team Members의 팀원 정보
- Projects의 프로젝트 정보
- Tasks의 업무 필드와 연결 관계
- 원본 Notion 페이지 링크

Notion 페이지 본문, 문서 DB, 파일은 이전하지 않는다. 필요한 경우 원본 링크로 접근한다.

### 10.2 이전 전 검토

변환 결과를 바로 확정하지 않고 다음 항목을 검토 목록으로 만든다.

- 프로젝트가 없는 태스크
- 담당자가 없거나 여러 명인 태스크
- 여러 프로젝트에 연결된 태스크
- 완료 시각이 없는 완료 태스크
- 생성 시각보다 완료 시각이 앞선 기록
- 기한이 오래됐거나 없는 미완료 태스크
- 새 상태 체계로 변환할 때 의미 확인이 필요한 프로젝트

대표 담당자·대표 프로젝트가 모호하면 수동 지정한다. 불명확한 원본 날짜를 임의로 만들어 넣지 않는다.

### 10.3 변환 규칙

- 기존 태스크 ‘일시 중단’은 미완료 상태와 막힘 정보로 변환하되 사유를 확인한다.
- 완료 시각이 없는 과거 태스크는 ‘완료 시각 미상’으로 보존한다.
- 완료 시각 미상 업무는 특정 주의 완료 실적에 임의 배정하지 않는다.
- 원본 생성 시각과 시스템 가져오기 시각을 구분한다.
- 프로젝트의 ‘정지·지원 종료·완료’는 원래 의미를 확인하고 변환한다.
- 같은 Notion ID를 다시 가져와도 중복 생성하지 않는다.

이전 검수 후 신규 업무 작성 위치를 새 시스템으로 전환한다. 원본 Notion 데이터는 검수가 끝날 때까지 보존한다.

## 11. 운영과 비기능 요구사항

### 11.1 구성

- 하나의 웹 애플리케이션과 하나의 관계형 DB를 기본으로 한다.
- 예약 작업은 같은 코드베이스에서 실행할 수 있도록 한다.
- 최초 버전에 별도 메시지 브로커·검색 서버·마이크로서비스를 도입하지 않는다.
- 알림 상태와 보고서는 DB에 저장해 재시작 후에도 처리 상태를 유지한다.
- 예약 실행이 겹쳐도 동일 작업을 동시에 처리하지 않도록 한다.
- 사용자 PC가 꺼져 있어도 예약 작업이 실행되는 배포 환경을 사용한다.

호스팅·DB·백업·AI 사용에 따른 비용은 별도로 발생할 수 있다.

### 11.2 백업과 복구

- 매일 자동 백업한다.
- 기본 백업 보존 기간은 30일로 한다.
- 백업은 운영 DB와 분리된 위치에 보관한다.
- 사용자·프로젝트·태스크·댓글·변경 이력·알림 설정을 복구할 수 있어야 한다.
- 운영 시작 전에 실제 복구 시험을 한 번 수행한다.
- 기본 복구 목표는 최근 성공한 일일 백업 시점이다.
- 관리자는 데이터와 관계를 보존하는 구조화된 내보내기를 실행할 수 있다.
- 복원 후 과거 알림이 다시 발송되지 않도록 발송 이력을 함께 복구한다.

### 11.3 상태 확인

관리자 화면에 다음을 표시한다.

- 마지막 예약 작업 실행 시각
- 마지막 주간 보고 결과
- 최근 알림 실패
- 마지막 백업 성공 시각
- AI 호출 실패와 사용량

애플리케이션 전체가 중단되면 내부 알림도 멈출 수 있으므로, 배포 환경의 외부 상태 확인 또는 관리형 장애 알림을 연결한다.

### 11.4 보안

- HTTPS를 사용한다.
- API 호출마다 인증과 권한을 검사한다.
- Discord 봇 토큰·연동 토큰과 AI 키는 서버 측 비밀 설정으로만 보관한다. 업무 DB·화면·오류 메시지·백업 내보내기에 넣지 않는다.
- 로그에 토큰·비밀키를 기록하지 않는다.
- 연동 토큰은 원문을 다시 조회할 수 없도록 저장한다.
- 외부 URL과 사용자 입력은 화면에 안전하게 표시한다.
- 업무 API에 기본 요청 제한을 적용한다.
- 운영 시작 후에도 의존성 보안 패치와 백업 실패 확인을 위한 최소 점검 절차는 유지한다.

### 11.5 사용성과 성능

초기 검증 기준은 활성 사용자 30명, 누적 태스크 10,000건, 동시 사용자 10명으로 가정한다. 실제 규모에 맞게 개발 착수 시 확정한다.

- 일반 목록·상세·저장 요청은 목표 부하에서 서버 응답의 95%가 1초 이내여야 한다.
- AI 요약과 외부 전송 시간은 위 응답 목표에서 제외한다.
- 긴 작업은 웹 요청을 기다리게 하지 않고 처리 상태를 표시한다.
- PC와 모바일에서 조회·생성·상태 변경이 가능해야 한다.
- 상태를 색상만으로 구분하지 않는다.
- 저장 실패와 수정 충돌은 사용자가 이해할 수 있는 문장으로 안내한다.

## 13. 개발 순서와 출시 조건

### 1단계: 업무 관리 기반

사용자 승인, 프로젝트, 태스크, 상태 처리, 변경 이력, 내 업무와 전체 현황판을 구현한다.

### 2단계: 운영 자동화

Discord 알림, 예약 작업, 발송 기록, 백업과 상태 확인을 구현한다.

### 3단계: AI 연계

공통 API 기반 MCP 도구, 제한된 연동 권한, 주간 요약과 실패 시 기본 보고를 구현한다.

### 4단계: 이전과 시범 운영

대표 프로젝트를 먼저 이전하고 두 차례 주간 보고 주기 동안 사용한다. 필수 검수 시나리오와 실제 백업 복구가 통과하면 전체 업무를 전환한다.

출시 전에 확정할 운영 설정:

- 초기 관리자와 가입 승인 담당자
- 실제 사용자 규모와 배포 환경
- Discord 봇 설치, 팀 공통 채널, 발송 시간
- AI 제공업체·모델·사용 한도
- 백업 저장 위치와 장애 통보 수신자
- Notion 데이터 전환일과 예외 데이터 처리 담당자
